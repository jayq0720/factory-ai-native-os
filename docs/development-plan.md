## 1. 产品定位

一句话：**让一家没有任何信息化系统的工厂，跳过"先上 MES/ERP"，直接由一个常驻在线的工厂 Agent 承担录入、追溯、监控、分析和提醒。**

两份参考资料在本项目里的分工：

- **阿里云手册**回答"系统由哪些责任层组成、怎么治理"：五个责任域、三个平面、AI 网关、权限与证据。
- **DeepSeek Super-agent**回答"Agent 怎么在工厂里持续工作"：工人和老板面对的始终是**同一个工厂 Agent**，它同时在钉钉/企业微信/飞书和设备数据之间工作，自己处理事件、并行推进多个任务，不需要人逐条下指令。

| 传统数字化 | 工厂 AI Native OS |
|---|---|
| 先上 MES/ERP，再做数据，再做 AI | 一开始就由 Agent 承担录入、整理、分析、提醒 |
| 工人填表单 | 工人在已有 IM 里**拍照、语音、说话** |
| 人去看报表、找问题 | Agent **主动**盯数据，有事才说，没事保持安静 |
| 每家工厂定制开发 | **核心 OS + 行业包 + 租户配置** |

## 2. 总体架构

### 2.1 五个责任域（阿里云手册第 2 章）

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ① 业务与应用层                                                              │
│   行业包（耐火材料 / 后续其他行业）│ 钉钉 / 企业微信 / 飞书 │ Web 控制台 │ 大屏       │
├──────────────────────────────────────────────────────────────────────────┤
│ ② Agent 构建与编排层（Harness，按 Super-agent 双层架构，见 2.4）              │
│   Router（工厂总管）│ Worker（任务执行）│ Context(Inline & Spill) │ Memory │ Skill │ Tool │
├──────────────────────────────────────────────────────────────────────────┤
│ ③ 生产运行层                                                                │
│   Trigger 事件总线 │ 状态存储（事件日志、Thread、Checkpoint）│ AI 网关 │ Watchdog     │
│   厂端 daemon：fos-edge（Rust，设备采集 + 受控执行）                            │
├──────────────────────────────────────────────────────────────────────────┤
│ ④ 治理与控制层                                                              │
│   租户与身份 │ 工具分级权限 │ 人工审批 │ 预算 │ Agent Release 版本 │ 审计证据           │
├──────────────────────────────────────────────────────────────────────────┤
│ ⑤ 调优层                                                                    │
│   Trace/成本观测 │ 黄金数据集 │ Badcase 回归 │ Prompt/Skill/过滤规则迭代              │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.2 三个平面 + 存算分离

阿里云手册的三个平面，和 Super-agent 第 5 节"计算、状态与环境分离"是同一个思路，合在一起就是本项目的部署原则：

| 平面 | 放在哪 | 装什么 | 原则 |
|---|---|---|---|
| 执行面（计算） | 阿里云 ECS 容器 | Router、Worker、OCR 推理、IM 适配器 | **无状态**，可随时重启、替换、扩容 |
| 数据与资源面（状态） | 阿里云 RDS PostgreSQL + OSS | 业务数据、Trigger/Thread/Session、时序、向量、单据原件 | 所有会话与任务状态外置，Agent 不依赖某台机器活着 |
| 执行环境（手） | **工厂现场** | fos-edge daemon：连仪表、PLC、摄像头；断网缓存 | 重状态的设备环境留在原地，daemon 只负责执行命令、返回结果，不保存会话 |
| 控制面 | 阿里云 | 租户、身份、策略、Agent Release、审计、评估 | 集中定义，判定点分布；控制面故障不阻断现场录入和采集 |

这样工厂断网时：fos-edge 继续采集并本地缓存；恢复网络后补传，云端 Agent 自动处理积压事件（对应 Super-agent "支持间歇在线的设备"）。

### 2.3 AI 网关三层

| 层 | 粒度 | 职责 | 选型 |
|---|---|---|---|
| LLM 网关 | 每次模型调用 | 统一 OpenAI 兼容接口；百炼（Qwen、DeepSeek）/ DeepSeek 官方 / 火山方舟 / 本地模型路由、降级、限流、按租户计 Token 成本 | **LiteLLM** 起步；量大后评估 Higress（阿里开源 AI 网关） |
| MCP 网关 | 每次工具调用 | 工具注册、工具级 ACL、凭证托管、审计 | 自研（Python，MCP 官方 SDK） |
| Agent 网关 | 每个事件/任务 | 三种 IM 的消息统一成 Trigger、租户配额 | 自研，即 2.4 的 Trigger 入口 |

### 2.4 Agent 运行模型：工厂 Super-agent（DeepSeek）

#### 2.4.1 双层架构：Router + Worker

```
   钉钉 / 企业微信 / 飞书     设备告警（fos-edge）     定时任务      OCR 完成      Web 控制台
            │                     │                │            │             │
            └──────────────┬──────┴────────────────┴────────────┴─────────────┘
                           ▼
                 ┌──────────────────────┐
                 │ Trigger 入口 + 两级过滤 │  Fast Path：代码规则   Slow Path：LLM 判断
                 └──────────┬───────────┘
          已订阅 Thread ──────┼───────── 新事件
          （程序直通）         │            ▼
                 │           │   ┌──────────────────┐
                 │           │   │ Router：工厂总管    │  常驻、轻量模型、不直接干活
                 │           │   │ 统一对外回复、全局记忆 │  只做：理解、分派、汇总、回复
                 │           │   └────────┬─────────┘
                 ▼           ▼            ▼ 分派
        ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
        │Worker:  │ │Worker:  │ │Worker:  │ │Worker:  │   上下文互相隔离，挂完整工具
        │拍照录单  │ │批次追溯  │ │窑炉异常  │ │日报生成  │   用最强模型；向 Router 汇报
        └─────────┘ └─────────┘ └─────────┘ └─────────┘
                           ▲
                  Watchdog（独立 Control Loop，定时巡检）
```

| 层 | 职责 | 模型 |
|---|---|---|
| **Router（工厂总管）** | 每个租户（工厂）一个常驻 Session；承接所有人的消息和事件；判断要不要管、交给谁；所有对人的回复都由它发出；维护全局记忆 | 轻量快速模型（如 Qwen3 中小尺寸 / DeepSeek-V3 非思考模式）；积压事件自动合并成一批处理（Batching） |
| **Worker** | 一个任务一个 Worker，上下文隔离，挂完整工具；内部可以再拆子任务；不直接对人说话，只向 Router 汇报 | 按任务选：录单用 Xiaomi-OCR-0 + DeepSeek-V3；根因分析用 DeepSeek-R1；视觉用 Qwen-VL |

为什么适合工厂：班组长在群里同时说"3 号窑温度不对"、"这张送货单帮我录一下"、"昨天合格率多少"，三件事会被分给三个 Worker 并行处理，互不打断；工人始终只面对"一个工厂助手"，不需要管理会话。

#### 2.4.2 事件驱动（Trigger）

驱动 Agent 的不是人逐条输入，而是工厂里的各种事件：

| Trigger 来源 | 例子 |
|---|---|
| IM 消息 | 群聊文字、照片、语音、卡片按钮点击（三种 IM 统一格式） |
| 设备事件 | fos-edge 上报的超温、断偶、窑车推进间隔异常、数据中断 |
| 定时 | 每日 7:00 日报、每班交接提醒、抄表提醒 |
| 系统事件 | OCR 完成、检验结果不合格、库存低于阈值 |

**两级过滤**（Fast Path / Slow Path）：

- **程序层（Fast Path）**：确定性规则，零模型成本。例如：图片消息 → 直接进 OCR 录单流程；闲聊群只响应 @；设备数值在正常范围 → 只入库不触发 Agent；超温超过硬阈值 → 规则直接告警。
- **语义层（Slow Path）**：通过程序层的候选事件交给 Router 的 LLM 判断要不要行动。策略写在提示词里，**工厂管理员可以用自然语言增删规则**（如"以后原料检验单都要抄送质检主管"）。

**Thread 与订阅直通**：同一个 IM 话题、同一个批次、同一窑次、同一个告警，构成一个 Thread。Worker 创建后订阅相关 Thread，后续事件由程序直接送到该 Worker，不再经过 Router，降低 Router 负载和 Token 开销。

#### 2.4.3 上下文组织：Inline & Spill + 链式召回

工厂数据量大（时序曲线、长单据），不能全部塞进上下文：

- **Inline**：只放当前对象的 ID + 摘要 + 紧邻关联对象（如批次号、窑次号、最近 3 条相关消息）。
- **Spill**：长内容（完整温度曲线、整张检验报告）留在库里，上下文只放引用和摘要，模型需要时用工具读取。
- **链式召回**：Trigger、Thread、批次、窑次、检验单等对象都有唯一 ID 并互相引用，构成引用图。Agent 可以从"这批砖不合格"一路追到"用的哪批原料 → 哪一窑 → 那一窑的温度曲线"。这与批次追溯天然契合。

#### 2.4.4 主动与投机执行

借鉴 Super-agent 的"静默复现并修复"：

- 群里有人说"今天 2 号窑的砖好像有点裂"，Agent **先在后台**拉取该窑次温度曲线、原料批次、近期同类问题，只有找到有价值的线索才回复，否则保持安静。
- 设备出现临界趋势（还没超阈值）时，后台先准备好分析和建议，真正超限时立刻给出。
- 所有投机结果只是**建议（L1）**，不执行任何写操作。

#### 2.4.5 全双工交互与多信道输出

- **异步工具调用**：耗时操作（OCR 批量识别、长时段数据分析）用 `start()`/`stop()` 异步执行，Agent 不阻塞，期间仍可回应新消息。
- **IM 输出规范**：像同事一样，只在需要确认或有结论时说话；单条回复不超过约 100 字；确认用卡片按钮。长内容（日报、分析报告）生成为控制台页面或文档，IM 里只发摘要 + 链接。

#### 2.4.6 Watchdog

独立于主系统的 Watchdog Session，用定时消息驱动：

- 基础设施：IM 连接、模型 API、数据库、OCR 服务是否正常。
- **现场**：各厂 fos-edge 是否在线、每个点位数据是否按时到达（"3 号窑 20 分钟没数据"比"超温"更早暴露问题）。
- 任务进展：Worker 是否卡住、是否在无效循环、是否偏离目标；异常时介入重启或上报。
- 维护者可以用自然语言问 Watchdog "昨晚为什么没发日报"。

### 2.5 模型分层调用

| 链路 | 时延 | 模型 | 例子 |
|---|---|---|---|
| 实时控制 | 毫秒级 | **不用大模型**，fos-edge 规则 | 超温硬告警 |
| 事件过滤 | 毫秒级 | 程序规则（Fast Path） | 丢弃噪声 |
| 感知 | 秒级 | Xiaomi-OCR-0、Qwen-VL | 单据/记录纸/仪表照片 → JSON |
| Router 判断与回复 | 1–4s | 轻量快速模型，批处理 | 理解、分派、回复 |
| Worker 执行 | 秒～分钟 | DeepSeek-V3 系列 / Qwen3 | 录单、查询、工具调用 |
| 深度推理 | 分钟级，异步 | DeepSeek-R1 系列 / Qwen3 思考模式 | 质量根因、能耗分析 |
| 内容生成 | 异步 | Seedance | SOP、安全培训短视频 |

### 2.6 Agentic OS 核心对象（阿里云手册第 30 章 + Super-agent）

| 对象 | 含义 |
|---|---|
| Tenant | 一家工厂 |
| Agent 身份 | Router、各类 Worker、Watchdog 各自独立授权、审计，与"人"的操作区分 |
| Trigger | 一条进入系统的事件 |
| Thread | 一条事件流（IM 话题、批次、窑次、告警） |
| Run / Worker Session | 一次任务运行，可暂停、恢复，订阅若干 Thread |
| Skill | 行业包里可版本化的方法（如"解析耐火制品理化检验报告"） |
| Tool / MCP 端点 | 可调用能力，独立注册与授权 |
| Edge Node | 厂端 fos-edge daemon，持有设备凭证，云端只发受控命令 |
| Budget Lease | 每个租户/Run 的 Token 与费用上限 |
| Policy | 工具权限、审批规则、过滤规则、数据出域规则 |
| Evidence | 计划、已执行操作、已确认结果的记录 |

### 2.7 自治阶梯与安全

| 级别 | 行为 | 本项目使用范围 |
|---|---|---|
| L1 建议 | 只出方案，人执行 | 窑炉参数、配方调整、根因分析、所有投机执行的结果 |
| L2 单步获准 | 每次写入前人工确认 | 拍照录单（卡片点"确认"才入库）、出入库 |
| L3 有界自主 | 限定范围内连续执行 | 日报、数据汇总、提醒推送、Watchdog 自愈 |
| L4/L5 | 长期自主/跨组织 | 3 个月内不做 |

安全红线（呼应 Super-agent 第 8.4 节"安全与隐私"开放问题）：

1. Agent **不写任何设备控制量**；fos-edge 只暴露白名单内的**只读**命令。
2. 设备与系统凭证只存在于 fos-edge 和凭证托管里，**永远不进入模型上下文**。
3. 云端被攻破时的影响半径：fos-edge 只接受签名的白名单命令，不能执行任意 shell。
4. IM 群消息属于不可信输入，提示注入防护 + 写操作一律走 L2 确认。

## 3. 首个行业：隔热耐火材料

### 3.1 典型工艺与数据（W1 现场调研核实）

```
原料进厂/检验 → 配料 → 混炼 → 成型（压制/浇注/挤出）→ 干燥 → 烧成（隧道窑/梭式窑）→ 加工 → 理化检验 → 包装入库 → 发货
```

| 环节 | 现在大概率的记录方式 | OS 如何接入 |
|---|---|---|
| 原料进厂与检验 | 纸质送货单、化验单 | 拍照 → Xiaomi-OCR-0 → 结构化 → 工人确认 |
| 配料/混炼 | 手写配料记录 | 拍照或语音；配方入库后 Agent 自动核对 |
| 成型/干燥 | 班组记录本 | 拍照/语音 |
| 烧成 | 温控仪表 + 记录纸/人工抄表 | 见 3.2 三条路径 |
| 理化检验 | 纸质检验报告（体积密度、导热系数、耐压强度、加热永久线变化、耐火度等） | 拍照 → OCR 表格解析 → 自动判定 → 关联批次 |
| 库存/发货 | Excel 或手工账 | 导入 Excel + 对话式出入库 |
| 能耗 | 电表/燃气表抄表 | 拍照抄表，或加装带通讯的智能表 |

### 3.2 窑炉与设备接入：三条路径

窑炉和仪表型号未知，fos-edge 按"能联网 → 改造后联网 → 不能联网"三档设计，**同一个窑可以混用**，数据最终进入同一张时序表，只是 `source` 和精度标记不同。

| 路径 | 适用情况 | 做法 | 数据频率 | 成本/工作量 |
|---|---|---|---|---|
| **A. 直接联网** | 温控仪表有 RS485（Modbus RTU）；或 PLC/触摸屏有以太网（Modbus TCP、OPC UA、西门子 S7） | 工控机/网关盒子跑 fos-edge，直接读寄存器；仪表通讯参数（地址、波特率、寄存器表）写进租户配置 | 秒级 | 低：一台工控机 + RS485 转换器 |
| **B. 改造后联网** | 仪表没有通讯口，或不允许接入控制系统 | **旁路加装**，不动原控制回路：① 在测温点附近加装热电偶 + 带 RS485 的温度变送器/采集模块；② 或用无线测温模块（LoRa / 4G）；③ 能耗加装带 RS485 的电表/燃气表 | 秒～分钟级 | 中：需电工现场施工 |
| **C. 不能联网** | 无法改造、临时过渡，或某些老设备 | ① 固定摄像头定时拍仪表盘 → 视觉读数（Qwen-VL / OCR）；② 工人按提醒拍照仪表或记录纸 → Xiaomi-OCR-0；③ 语音/手动报数 | 分钟～小时级 | 最低，但精度和频率有限 |

**网络条件**也分三档：

| 现场网络 | 方案 |
|---|---|
| 车间有有线/WiFi 外网 | fos-edge 直接上行阿里云 |
| 车间无网 | 4G/5G 工业路由器上行 |
| 网络时有时无 | fos-edge 本地缓存（默认至少 7 天），恢复后补传；Watchdog 区分"断网"和"设备故障" |

fos-edge 的驱动按插件设计（`modbus-rtu`、`modbus-tcp`、`opcua`、`s7`、`camera-snapshot`、`manual`），换工厂、换行业只加配置或新驱动。

### 3.3 首批场景（3 个月内交付）

| 优先级 | 场景 | Super-agent 机制 | 模型/组件 |
|---|---|---|---|
| P0 | **拍照/语音录单** | Fast Path 直达录单 Worker；L2 卡片确认 | Xiaomi-OCR-0 + DeepSeek/Qwen |

| P1 | **窑炉监控** | 设备 Trigger + 两级过滤；超差告警；投机执行预分析 | fos-edge + 规则 + DeepSeek-R1 |
| P1 | **质量分析** | 不合格 Trigger → 后台根因分析，L1 建议 | DeepSeek-R1 |

| P2 | **SOP / 安全培训视频** | 异步工具 | DeepSeek + Seedance（视进度，可能放到 3 个月后） |

## 4. AI for Engineering：从客户技术文件、招标文件到方案与报价

隔热耐火材料企业的销售高度依赖"工程技术"：客户发来窑炉/工业炉的技术要求或招标文件，工程师要读几十到几百页资料，确定工况，选材料、定衬里结构、算用量、出技术方案和报价。这个环节慢、依赖少数资深工程师、容易漏条款。AI for Engineering 把它做成一条**有原文出处、每一步都可人工修改、最后必须人工审核**的流水线。

它和生产侧共用同一套核心 OS：同一个文档解析服务（Xiaomi-OCR-0）、同一个 Router/Worker 运行模型、同一套治理与证据链，并新增一个可维护的**工程知识库**。

### 4.1 两个应用

| 应用 | 输入 | 输出 |
|---|---|---|
| **A. 技术文件 → 方案与报价** | 客户技术要求、技术协议、窑炉图纸（PDF/扫描件）、现场照片、Excel 工程量清单 | 结构化工况字段（带页码引用）→ 推荐产品组合与衬里结构 → 可编辑的技术方案、BOM/材料清单、报价草稿 → 风险与缺失信息清单 |
| **B. 招标/需求文件解析与拆解** | 招标文件、询价函、需求说明书（通常 50–300 页） | 项目概况与时间节点 → 条款逐条拆解的需求矩阵（★实质性条款、废标条款单独标出）→ 技术/商务偏离表草稿 → 投标资料清单 → 拆出来的技术需求直接进入应用 A |

### 4.2 应用 A 流程

```
上传文件 ─► 文档解析 ─► 字段抽取（带页码引用）─► 人工核对字段
                                              │
          ┌───────────────────────────────────┘
          ▼
   知识库匹配产品组合 + 衬里结构 ─► 传热与用量计算（代码，不由模型估算）
          │
          ▼
   生成草稿：技术方案 / BOM / 报价 ─► 人工编辑 ─► 审核（风险、缺失信息）─► 确认发布
```

| 步骤 | 做什么 | 实现 |
|---|---|---|
| 1. 上传 | Web 控制台拖拽上传，或在 IM 里把文件发给工厂助手；一个"工程项目"下可以有多份文件 | 原件存 OSS，计算哈希防重复 |
| 2. 文档解析 | **有文字层的 PDF 直接取文字**（快、准）；扫描件和图片逐页走 Xiaomi-OCR-0，输出每页 Markdown（表格为 HTML）；规整文档可开启版面区域模式（PP-DocLayoutV3）拿到区域坐标；Word/Excel 直接读取 | `pypdfium2`、`pdfplumber`、`python-docx`、`openpyxl`；注意不用 AGPL 许可的 PyMuPDF |
| 3. 字段抽取 | 按行业包里的工程 Schema 抽取字段，**每个字段必须带原文引用**：页码、原文片段、（区域模式下）坐标、置信度；找不到的字段标"缺失"，不允许模型编造 | DeepSeek-V3 结构化输出 + Xiaomi-OCR-0 的字段抽取能力；长文档按页切块，Inline & Spill |
| 4. 人工核对 | 左边原文页面、右边字段表；点字段跳到对应页并高亮原文；可直接改值，修改留痕 | Web 控制台 |
| 5. 知识库匹配 | 按工作温度、气氛、部位、热震、荷载等筛选可用产品，再组合成衬里结构（工作层 / 隔热层 / 保温层）；给出 2–3 个备选方案及理由 | 规则过滤（硬约束：分类温度 ≥ 工作温度 + 安全余量、化学相容）+ DeepSeek-R1 解释与权衡 |
| 6. 计算 | 多层平壁/圆筒一维稳态传热：校核外壁温度、热损失；按面积/体积、密度、损耗率算各材料用量（m³、t、块数、卷数） | **Python 确定性计算**，结果和公式一起展示；模型只调用、不估算 |
| 7. 生成草稿 | 技术方案（工况、选材理由、衬里结构图表、施工要点、执行标准）、BOM（规格、数量、单位、损耗）、报价（单价取自知识库价格表版本、可选施工费/运费/税） | 模板 + DeepSeek 撰写；导出 Word / Excel / PDF；控制台在线编辑 |
| 8. 审核 | 自动生成风险与缺失清单；工程师逐条处理后确认；报价需销售负责人二次确认 | 自治级别：草稿 L1，发布 L2 |

#### 工程字段 Schema（耐火材料行业包初版，W5 与业务核对）

| 分组 | 字段 |
|---|---|
| 项目 | 客户名称、项目名称、项目地点、交货期/工期、交货方式 |
| 设备与部位 | 炉型（隧道窑、梭式窑、辊道窑、回转窑、加热炉、热处理炉、焚烧炉、电炉等）、部位（炉顶、炉墙、炉底、炉门、烟道、窑车等）、几何尺寸 |
| 工况 | 正常工作温度、最高温度、升降温制度/热震、气氛（氧化/还原/含碱/含硫/含氢等）、介质侵蚀、荷载与磨损、外壁温度要求、热损失要求 |
| 衬里 | 现有或要求的衬里结构、各层材料、各层厚度、总厚度、锚固方式 |
| 标准与验收 | 执行的施工与验收标准（如工业炉砌筑相关国家标准、行业标准、企业标准）、检测要求、质保期 |
| 工程量 | 面积（m²）、体积（m³）、重量（t）、数量清单 |
| 商务 | 报价有效期、付款方式、税率、包装运输要求 |

每个字段的数据结构：`{ 值, 单位, 来源: [{文件, 页码, 原文片段, 坐标?}], 置信度, 状态: 已抽取/人工修改/缺失, 数据模式: real/mock }`。

### 4.3 应用 B：招标/需求文件解析与拆解

| 步骤 | 输出 |
|---|---|
| 1. 结构识别 | 识别章节结构：招标公告、投标人须知、评标办法、合同条款、技术规格书、工程量清单、投标文件格式 |
| 2. 关键信息 | 项目名称、招标编号、预算/最高限价、投标截止与开标时间、保证金、资格要求、联系人；截止时间自动在 IM 里设提醒 |
| 3. 条款拆解 | 逐条拆成**需求矩阵**：条款编号、原文、页码、类别（技术/商务/资格/格式）、是否实质性（★/▲/"必须"/"不得"）、是否可能导致废标、建议响应、负责人、状态 |
| 4. 偏离表草稿 | 技术与商务条款逐条对照我方产品能力（来自知识库），标"无偏离 / 正偏离 / 负偏离 / 待确认" |
| 5. 评分点分析 | 按评标办法列出得分项和对应需要准备的证明材料 |
| 6. 资料清单 | 需要提交的资质、业绩、检测报告、授权书等清单，与知识库里已有的资料自动对上，缺的标出来 |
| 7. 转入应用 A | 技术规格书里抽出的工况和工程量直接生成工程项目，进入选材与报价流程 |

### 4.4 可维护的工程知识库

知识库是这套功能能否落地的关键，必须让业务人员自己能维护，并且有版本。

| 内容 | 主要字段 | 维护方式 |
|---|---|---|
| 产品库 | 牌号、类别（轻质隔热砖、莫来石砖、氧化铝空心球制品、硅酸铝纤维毯/板/模块、轻质/重质浇注料、可塑料、耐火泥浆、锚固件等）、分类温度/最高使用温度、体积密度、不同温度下导热系数、耐压强度、加热永久线变化、化学成分、规格、包装、单位 | 控制台表单 + Excel 批量导入；检测报告拍照 OCR 补录 |
| 价格表 | 牌号、单价、单位、生效日期、客户类别 | 单独版本化；报价草稿记录引用的价格版本 |
| 衬里结构模板 | 炉型 + 部位 + 温度区间 → 推荐的分层结构与厚度范围 | 由资深工程师维护，历史方案沉淀 |
| 标准条款库 | 施工与验收标准的关键条款摘要与适用范围 | 标准原文由企业合法获取后导入，只做检索与引用 |
| 历史项目 | 过去的技术方案、报价、中标/未中标结果 | 上传后自动解析入库，用于相似项目推荐 |
| 资质与资料 | 营业执照、资质证书、检测报告、业绩合同 | 用于招标资料清单自动匹配，带有效期提醒 |

维护规则：所有修改留痕可回滚；AI 只能**提议**修改知识库（例如"从这份检测报告里识别到 LN-1260 导热系数更新"），由管理员确认后生效（L2）。

### 4.5 审核：风险与缺失信息提示

| 类型 | 例子 |
|---|---|
| 缺失 | 没有给出气氛、最高温度、外壁温度要求、执行标准；工程量缺单位 |
| 冲突 | 不同页给出的工作温度不一致；技术要求与工程量清单厚度不一致 |
| 选材风险 | 产品分类温度余量不足；还原/含碱气氛下选了不适合的材料；外壁温度计算不达标 |
| 商务风险 | 质保期、付款比例、违约条款异常；报价低于成本线；价格表版本过期 |
| 招标风险 | ★实质性条款未响应、负偏离、资格材料缺失或过期、截止时间临近 |

每条提示都带原文页码和建议处理方式；工程师逐条标"已处理 / 接受风险 / 不适用"后才能确认发布。

### 4.6 界面

Web 控制台新增"工程"模块：

1. **工程项目列表**：客户、项目、状态（解析中 / 待核对 / 方案编辑中 / 待审核 / 已发布）、截止时间。
2. **文档解析页**：左侧原文页面预览（翻页、缩放），右侧解析结果与字段表；点字段定位到原文并高亮；每页显示解析方式（文字层 / OCR / 模拟）。
3. **选材页**：备选方案对比（产品组合、分层厚度、外壁温度、用量、材料成本）。
4. **方案编辑页**：技术方案在线编辑器 + BOM 表格 + 报价表格，三者联动（改厚度 → 用量与报价自动重算）。
5. **审核页**：风险/缺失清单逐条处理，确认后导出 Word / Excel / PDF。
6. **招标拆解页**：需求矩阵表格（可筛选★条款、负偏离、未处理）、偏离表、资料清单、时间节点。
7. **知识库管理页**：产品、价格、模板、标准、资料的增删改与导入，修改历史。

IM 侧：把文件发给工厂助手即可创建工程项目；解析完成后助手回一句摘要和控制台链接；截止时间提醒、审核待办推送到 IM。

**模拟模式（没有真实模型服务时）**：文档解析服务定义统一的 `OcrProvider` 接口，有 `real`（调用 vLLM 上的 Xiaomi-OCR-0）和 `mock`（返回预置样例结果）两个实现，由配置切换。模拟模式下：

- 所有接口响应带 `"data_mode": "mock"`，每个字段带 `data_mode` 标记；
- 界面顶部固定显示"模拟数据，非真实识别结果"横幅，字段旁有"模拟"标记；
- 模拟结果**不能**审核发布、不能导出为正式文件，只能用于演示和前端开发；
- real 与 mock 不会在同一个项目里静默混用。

这样在 OCR 服务部署好之前（W2 前）界面和接口就可以先开发和演示。

### 4.8 在整体架构中的位置

- **Workers**：文档解析、字段抽取、选材匹配、方案撰写、招标拆解、审核，各自独立并行；一个工程项目 = 一个 Thread，后续上传的补充文件直通对应 Worker。
- **Router**：IM 里收到文件时判断是技术文件还是招标文件，创建项目并分派；对外只发摘要与链接。
- **Watchdog**：盯解析任务是否卡住、招标截止时间是否临近。
- **模型**：Xiaomi-OCR-0（解析）、DeepSeek-V3（抽取、撰写）、DeepSeek-R1（选材权衡、风险分析）、Qwen-VL（照片和图纸中的表格/标题栏）、Qwen Embedding（历史项目和标准检索）。
- **治理**：草稿永远是 L1；发布、报价、知识库修改都是 L2 人工确认；每个结论都能追到原文页码或知识库版本。
- **边界**：CAD 原生格式（DWG）解析、自动出施工图不在 3 个月范围内；图纸只解析 PDF/图片中的标题栏、表格和标注文字。

## 5. IM 接入：钉钉、企业微信、飞书都支持

三种 IM 通过**统一信道适配层**接入，Router 和 Worker 只看到统一的 Trigger 和统一的回复接口，不关心平台差异。

| 统一能力 | 钉钉 | 企业微信 | 飞书 |
|---|---|---|---|
| 接收消息（文字/图片/语音/文件） | 企业内部应用机器人，**Stream 模式**（长连接，无需公网回调地址） | 自建应用 / 智能机器人，**回调 URL** 模式（需公网 HTTPS 域名，具体可信域名/IP 要求以官方最新文档为准） | 企业自建应用，**事件订阅长连接**模式（无需公网回调地址） |
| 发送消息 | 机器人消息 / 工作通知 | 应用消息 / 群机器人 | 机器人消息 |
| 确认卡片 | 互动卡片 | 模板卡片 | 消息卡片 |
| 组织架构同步 | 通讯录 API | 通讯录 API | 通讯录 API |
| 免登进控制台 | 钉钉 H5 微应用免登 | 企业微信网页授权 | 飞书网页应用免登 |

设计要点：

- `fos/channels/` 下每个平台一个适配器，实现同一接口：`receive() → Trigger`、`send(text|card)`、`on_card_action()`、`sync_directory()`、`resolve_user()`。
- 一个工厂可同时启用多个 IM；同一个人在不同 IM 的身份映射到同一个系统用户。
- 卡片用统一 DSL 描述（标题、字段、按钮），由各适配器渲染成平台卡片。
- 开发顺序：**先做钉钉或飞书**（长连接模式，本地开发调试不需要公网域名），W3 跑通；企业微信在 W9 补齐。如果六安绿能实际只用其中一种，则先做那一种。

## 6. 技术选型（2 人团队，阿里云为主）

原则：**能用托管服务就不自建，能用一个组件就不用三个**。

### 6.1 阿里云部署（默认）

| 组件 | 选型 | 说明 |
|---|---|---|
| 大模型 | **阿里云百炼**（Qwen、DeepSeek 均可调用） | 主力 |
| 备用大模型 | DeepSeek 官方 API | 百炼故障时 LiteLLM 自动切换 |
| 视频生成 | 火山方舟 Seedance API | 唯一使用火山引擎的部分 |
| OCR 推理 | Xiaomi-OCR-0 + vLLM，部署在阿里云 **PAI-EAS** 或 GPU 型 ECS | 0.8B 模型，单张中端 GPU 足够；按量/抢占式降低成本 |
| 应用服务器 | ECS + Docker Compose | 3 个月内不上 K8s |
| 数据库 | **RDS PostgreSQL** + pgvector（向量）+ 时序表（分区表，或扩展可用时用 TimescaleDB） | 一个库承载业务、事件、时序、向量；扩展可用性在 W1 确认 |
| 对象存储 | OSS | 单据原件、照片、视频 |
| 事件队列 | PostgreSQL 内的队列表（如 `pgmq`）；量大后换阿里云消息队列 | Trigger、Thread 订阅、异步任务 |
| 设备上行 | fos-edge → HTTPS/MQTT → 云端；量大后评估阿里云物联网平台 | |
| 日志与观测 | 阿里云 SLS + 自托管 Langfuse（Agent Trace、Token 成本） | |
| 密钥 | 阿里云 KMS / 凭据管家 | 凭证不落代码、不进上下文 |

### 6.2 Rust 与 Python 分工

| 模块 | 语言 | 理由 |
|---|---|---|
| `fos-edge` 厂端 daemon（采集驱动、断网缓存、白名单命令执行、签名校验、上行） | **Rust** | 长期无人值守运行在工控机上，要求稳定、低资源、安全边界清晰；`tokio-modbus`、`async-opcua`、`rumqttc` 可直接用 |
| `fos-protocol` 共享数据契约（Trigger、点位、命令） | Rust（同时生成 Python 类型） | 云与边共享 |
| Trigger 入口的 Fast Path 过滤 | Python 起步，量大后迁 Rust | 高频、确定性逻辑，适合后期下沉 |
| Router / Worker / Watchdog、MCP 工具、OCR 管线、行业包、IM 适配器、API | **Python** | 生态最全、迭代最快 |

### 6.3 本地部署硬件（型号待定，给出建议）

用于数据不能上云的客户、或想降低长期 API 成本的场景。同一套 Docker Compose 支持"全云 / 云 + 本地推理 / 全本地"，区别只在 LiteLLM 路由配置。

| 方案 | 建议配置 | 能跑什么 | 适合 |
|---|---|---|---|
| **NVIDIA DGX Spark**（首选） | 单台，128GB 统一内存 | Xiaomi-OCR-0（vLLM/SGLang，官方支持路径）、Qwen3 中等尺寸、Embedding、Qwen-VL | 单厂本地推理；CUDA 生态与云上一致，迁移零改动 |
| **Mac Studio** | M3 Ultra，内存尽量大（≥ 256GB） | 量化后的较大模型（MLX / Ollama），Embedding | 想在本地跑更大的 Qwen / DeepSeek 量化模型；Xiaomi-OCR-0 在 macOS 上只有社区实验性版本，需实测后才能用于生产 |
| 组合 | DGX Spark 跑 OCR 和视觉，Mac Studio 跑大语言模型 | | 全本地、不依赖任何云 API |

建议先**不采购**，3 个月内全部用阿里云；W11 根据实际 Token 用量和客户需求再决定买哪种。

### 验收指标（建议，W1 后与工厂确认）

- 录单：核心单据字段识别准确率 ≥ 95%（确认后 100% 入库）；从拍照到确认 < 30 秒。
- 覆盖：≥ 80% 的纸质单据类型可通过系统录入。
- 并行：同一群里 3 件不同的事同时提出，互不阻塞，各自得到回复。
- 追溯：任一成品批次 10 秒内追溯到原料批次、窑次、检验结果。
- 窑炉：路径 A/B 断网 30 分钟数据不丢、超差 1 分钟内提醒；路径 C 按设定频率提醒抄表且无遗漏。
- 主动性：Agent 在 IM 中的无效打扰（被工人标记"不需要"）< 10%。
- 工程字段抽取：样本集上关键字段准确率 ≥ 90%，**100% 带原文页码引用**，找不到的字段 100% 标缺失而不是编造。
- 工程效率：从上传技术文件到出方案/BOM/报价初稿 ≤ 15 分钟（不含人工编辑）。
- 招标拆解：★实质性条款召回率 ≥ 95%，截止时间 100% 设提醒。
- 复制：新租户（同行业）部署 ≤ 1 天。
- 治理：所有写入 100% 有确认记录和证据链；凭证 0 次进入模型上下文。

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| 只有 2 人，范围过大 | 严格按 P0 → P1 → P2；每周演示后砍需求；能托管就不自建 |
| 工人不愿意用 | 入口放在已有 IM；拍照即可；Agent 话少、只在需要时说话；先找积极的班组长试点 |
| 窑炉无法直接联网 | 三条接入路径兜底（3.2），最差用拍照/摄像头读数 |
| Agent 主动打扰太多 | 两级过滤 + 工人可一键反馈"不需要"，反馈进入过滤规则迭代 |
| 手写单据识别不准 | Xiaomi-OCR-0 支持手写；L2 确认兜底；逐步把高频单据改成标准模板 |
| 大模型乱编数据 | 数字只来自数据库工具结果；回答附来源记录 |
| 云 API 成本 | Fast Path 过滤、Router 批处理、订阅直通、轻量模型做 Router、按租户预算上限 |
| 云端被攻破影响现场 | fos-edge 只执行签名白名单只读命令；凭证不出厂端 |
| 三种 IM 维护成本 | 统一适配器接口 + 卡片 DSL；先只做一种，W9 补齐 |
| AI 方案或报价出错造成商务损失 | 所有工程输出都是草稿；计算用确定性代码；每个字段和结论带页码或知识库版本；报价二次审核；模拟数据不能发布 |
| 工程知识库没人维护 | 表单 + Excel 导入 + AI 从检测报告和历史方案中提议更新，管理员一键确认 |
| 行业包抽象过早或过晚 | 先写在 `packs/refractory`，W13 用第二套租户验证 |
