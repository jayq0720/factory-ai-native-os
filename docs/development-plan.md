# 工厂 AI Native OS 开发方案（v0.2）

> 版本：v0.2 · 日期：2026-11-01 · 目标：3 个月（2026-11-02 ～ 2027-01-31）完成整体搭建，在首家试点工厂（六安绿能，隔热耐火材料）上线运行，并具备复制到其他工厂/行业的能力。

**v0.2 相对 v0.1 的主要变化**

1. 架构对齐阿里云《AI Agent HandBook》的参考架构（五个责任域、三个平面、AI 网关三层、Agentic OS 核心对象、自治阶梯）。
2. 试点行业确定为隔热耐火材料；工厂**目前没有任何信息化系统**，因此 OS 自身要承担"系统记录（System of Record）"的角色，第一入口是纸质单据数字化和 IM 对话录入。
3. 部署改为**云优先**，本地用 Mac Studio / NVIDIA DGX。
4. 小模型确定为 **Xiaomi-OCR-0**。
5. 团队只有 2 人（JayQ + Claude），范围、技术栈和路线图都按此大幅收敛。
6. 新增"核心 + 行业包 + 租户配置"的可复制设计。

## 1. 产品定位

一句话：**让一家没有任何信息化系统的工厂，直接跳过"先上 MES/ERP"，用 Agent + 对话 + 拍照的方式完成数字化和智能化。**

在阿里云手册第 30 章的四种"AI 操作系统形态"中，本项目属于**"功能层融合"**：模型、上下文与工具调用融入工厂的业务流程和任务管理，系统层提供运行、状态、治理与证据，业务语义留在行业包里。

与传统路线的区别：

| 传统数字化 | 工厂 AI Native OS |
|---|---|
| 先上 MES/ERP，再做数据，再做 AI | 一开始就由 Agent 承担录入、整理、分析、提醒 |
| 工人填表单 | 工人在钉钉/企业微信/飞书里**拍照、语音、说话** |
| 固定报表 | 随问随答 + Agent 自动生成日报 |
| 每家工厂定制开发 | **核心 OS + 行业包 + 租户配置**，复制到下一家只换配置和行业包 |

## 2. 总体架构（对齐阿里云 Agentic Application 参考架构）

### 2.1 五个责任域

阿里云手册把企业级 Agent 系统分为五个责任域，本项目的对应关系如下：

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ① 业务与应用层                                                              │
│   行业包（耐火材料 / 后续其他行业）│ 场景 Agent │ IM 入口 │ Web 控制台 │ 大屏          │
├──────────────────────────────────────────────────────────────────────────┤
│ ② Agent 构建与编排层（Harness）                                              │
│   模型路由 │ 任务循环/状态机 │ Context 构建 │ Memory │ Knowledge │ Skill │ Tool/MCP  │
├──────────────────────────────────────────────────────────────────────────┤
│ ③ 生产运行层                                                                │
│   Run 调度（异步/定时/事件触发）│ 状态存储（事件日志、Checkpoint）│ Workspace │       │
│   AI 网关（LLM 网关 / MCP 网关 / Agent 网关）│ 边缘采集 fos-edge(Rust)              │
├──────────────────────────────────────────────────────────────────────────┤
│ ④ 治理与控制层                                                              │
│   租户与身份 │ 工具分级权限 │ 人工审批 │ 预算 │ Agent Release 版本 │ 审计证据           │
├──────────────────────────────────────────────────────────────────────────┤
│ ⑤ 调优层                                                                    │
│   Trace/成本观测 │ 黄金数据集 │ Badcase 回归 │ Prompt/Skill 迭代 │（后期）微调        │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.2 三个平面

| 平面 | 本项目里装什么 | 原则 |
|---|---|---|
| 执行面 | Agent Worker、IM 机器人、OCR 推理、fos-edge 采集 | 无状态、可重启，不持有唯一真实状态 |
| 数据与资源面 | PostgreSQL（业务数据 + 时序 + 向量）、对象存储（照片/单据原件）、知识库、MCP 工具 | **状态外置**：任务、记录、证据全部落库，执行实例随时可替换 |
| 控制面 | 租户、身份、策略、Agent Release、审计、评估 | 集中定义，判定点分布在网关和工具层；控制面故障不阻断现场录入 |

### 2.3 AI 网关三层

| 层 | 粒度 | 本项目职责 | 选型 |
|---|---|---|---|
| LLM 网关 | 每次模型调用 | 统一 OpenAI 兼容接口；DeepSeek / Qwen / 豆包 / 本地模型路由、降级、限流、Token 成本按租户计量 | **LiteLLM**（Python，起步快）；量大后评估 Higress（阿里开源 AI 网关） |
| MCP 网关 | 每次工具调用 | 工具注册、工具级 ACL、凭证托管、审计 | 自研（Python，基于 MCP 官方 SDK），挂在 Agent 内核里 |
| Agent 网关 | 每个任务 | IM 消息 → 路由到对应 Agent、会话连续性、租户配额 | 自研，和 IM 接入合并 |

### 2.4 模型分层调用（DeepSeek 架构部分，待文章补充后修订）

| 链路 | 时延 | 模型 | 例子 |
|---|---|---|---|
| 感知 | 秒级 | Xiaomi-OCR-0、Qwen-VL | 单据/记录纸/仪表照片 → 结构化 JSON |
| 交互 | 1–5s | DeepSeek-V3 系列 / Qwen3 | 对话、录单、查询、工具调用 |
| 深度推理 | 分钟级，异步 | DeepSeek-R1 系列 / Qwen3 思考模式 | 质量异常根因、能耗分析、周报洞察 |
| 内容生成 | 异步 | Seedance | SOP、安全培训短视频 |
| 实时控制 | 毫秒级 | **不用大模型**，fos-edge 里的规则 | 超温报警 |

### 2.5 Agentic OS 核心对象（来自手册第 30 章，作为内核数据模型）

| 对象 | 在工厂 OS 中的含义 |
|---|---|
| Agent 身份 | 每个 Agent 是独立的、可授权、可审计的执行主体，与"人"的操作区分开 |
| Run | 一次任务运行（如"处理这张检验单"、"生成昨日日报"），可暂停、可恢复 |
| Session | 某个工人/班组在 IM 中的对话上下文 |
| Workspace | Run 的临时文件与中间产物（照片、OCR 中间结果） |
| Skill | 行业包里可复用、可版本化的方法（如"解析耐火砖理化检验报告"） |
| Tool / MCP 端点 | 可调用的能力（查库存、建批次、读窑温…），独立注册与授权 |
| Budget Lease | 每个租户/Run 的 Token 与费用上限 |
| Policy | 工具权限、审批规则、数据出域规则 |
| Evidence | 计划、已执行操作、已确认结果的记录，用于审计、追溯和评估 |

### 2.6 自治阶梯（决定 Agent 能"自己做"到什么程度）

| 级别 | 行为 | 本项目使用范围 |
|---|---|---|
| L1 建议 | 只出方案，人执行 | 窑炉烧成参数建议、配方调整建议、根因分析 |
| L2 单步获准 | 每次写入前人工确认 | **拍照录单默认级别**：Agent 识别后发卡片，工人点"确认"才入库 |
| L3 有界自主 | 在限定范围内连续执行 | 日报生成、数据汇总、提醒推送 |
| L4/L5 | 长期自主/跨组织 | 3 个月内不做 |

**红线**：Agent 不直接写任何设备控制量（窑炉、配料秤等），即使后续接入了控制接口也只能 L1。

## 3. 首个行业：隔热耐火材料

### 3.1 典型工艺与数据（需在 W1 现场调研中核实）

```
原料进厂/检验 → 配料 → 混炼 → 成型（压制/浇注/挤出）→ 干燥 → 烧成（隧道窑/梭式窑）→ 加工 → 理化检验 → 包装入库 → 发货
```

| 环节 | 现在大概率的记录方式 | OS 如何接入 |
|---|---|---|
| 原料进厂与检验 | 纸质送货单、化验单 | 拍照 → Xiaomi-OCR-0 → 结构化 → 工人确认 |
| 配料/混炼 | 手写配料记录 | 拍照或语音录入；配方存入系统后可由 Agent 核对 |
| 成型/干燥 | 班组记录本 | 拍照/语音 |
| 烧成 | 窑炉温控仪表 + 记录纸/人工抄表 | 优先：温控仪表 RS485/Modbus 采集（fos-edge）；其次：加装无线测温；兜底：拍照仪表/记录纸 OCR |
| 理化检验 | 纸质检验报告（体积密度、导热系数、耐压强度、加热线变化、耐火度等） | 拍照 → OCR 表格解析 → 自动判定合格与否 → 关联批次 |
| 库存/发货 | Excel 或手工账 | 导入 Excel + 对话式出入库 |
| 能耗 | 电表/燃气表抄表 | 拍照抄表或智能电表采集 |

### 3.2 首批场景（3 个月内交付）

| 优先级 | 场景 | 说明 | 模型/组件 |
|---|---|---|---|
| P0 | **拍照/语音录单** | 所有纸质单据、记录的统一入口；Agent 识别 → 结构化 → 卡片确认 → 入库并保留原件 | Xiaomi-OCR-0 + DeepSeek/Qwen + IM 卡片 |
| P0 | **批次追溯** | 自动把原料批次 → 配料 → 成型 → 烧成窑次 → 检验结果 → 发货串起来；"这批砖用的哪批原料、在哪一窑烧的" | Postgres + 知识图谱式关系表 + Agent 查询 |
| P0 | **工厂问答与日报** | 老板/班组长随时问产量、合格率、库存、能耗；每天早上自动推送日报 | DeepSeek-V3 / Qwen3 + Text-to-SQL 工具 |
| P1 | **窑炉烧成监控** | 采集温度曲线，对比工艺曲线，超差提醒；单位能耗统计 | fos-edge(Rust) + 规则 + DeepSeek-R1 分析 |
| P1 | **质量分析** | 检验不合格时，Agent 拉取原料、配料、烧成数据给出可能原因（L1 建议） | DeepSeek-R1 |
| P1 | **工艺知识助手** | 国家/行业标准、工艺卡、设备说明书问答 | RAG（pgvector）+ Qwen Embedding |
| P2 | **SOP / 安全培训视频** | 由工艺卡生成短视频脚本，Seedance 出视频 | DeepSeek + Seedance |

## 4. 可复制设计：核心 + 行业包 + 租户配置

为了从六安绿能扩展到其他公司和行业，代码从第一天就分三层：

| 层 | 内容 | 换一家同行业工厂 | 换一个行业 |
|---|---|---|---|
| **核心 OS**（行业无关） | Agent 内核、网关、IM 接入、OCR 管线、权限审计、数据底座、控制台 | 不变 | 不变 |
| **行业包**（如 `packs/refractory`） | 行业本体（工序、物料、指标定义）、单据模板与抽取 Schema、Skills、工具、Prompt、日报模板、评测集 | 不变 | 新写一个包，复用核心 |
| **租户配置** | 工厂的工序清单、配方、人员、设备点位、审批人、IM 组织 | 新配置（目标：1–2 天完成） | 新配置 |

行业包本身是可版本化的 Agent Release 组成部分，对应手册第 2.4 节"Agent Release 是生命周期的最小可复现单元"。

## 5. 技术选型（按 2 人团队收敛）

原则：**能用托管服务就不自建，能用一个组件就不用三个**。v0.1 里的 Kafka、Neo4j、Milvus、Keycloak、Temporal、K8s 等全部延后。

### 5.1 云上部署（默认）

| 组件 | 选型 | 说明 |
|---|---|---|
| 大模型 API | 阿里云百炼（Qwen、DeepSeek）、DeepSeek 官方 API、火山方舟（Seedance、豆包、DeepSeek） | LiteLLM 统一接入，按场景/成本路由，单一供应商故障可切换 |
| OCR 推理 | Xiaomi-OCR-0 + vLLM，部署在一台云 GPU 实例（阿里云 ECS GPU 或 PAI-EAS） | 0.8B 模型，单张中端 GPU 足够；也可放到本地 DGX 上 |
| 应用服务器 | 阿里云 ECS + Docker Compose | 3 个月内不上 K8s |
| 数据库 | **PostgreSQL**（阿里云 RDS）+ pgvector（向量）+ 时序表（按需 TimescaleDB 扩展或分区表） | 一个库承载业务、时序、向量，2 人可运维；扩展可用性需在 RDS 上确认 |
| 对象存储 | 阿里云 OSS | 单据原件、照片、视频 |
| 消息 | Postgres 队列（如 `pgmq`）或 Redis Streams | 先不引入 Kafka/NATS |
| IM 入口 | 钉钉 / 企业微信 / 飞书 三选一先做（看六安绿能实际在用哪个） | 工人不装新 App |
| 观测 | Langfuse（自托管，Agent Trace + 成本）+ 云监控 | 对应手册调优层 |

### 5.2 本地部署（数据敏感客户 / 离线场景）

| 硬件 | 适合跑什么 | 说明 |
|---|---|---|
| NVIDIA DGX（如 DGX Spark / DGX Station） | Xiaomi-OCR-0（vLLM/SGLang，官方支持路径）、Qwen3 中等尺寸、Embedding | CUDA 生态，和云上部署方式一致，**本地首选** |
| Mac Studio | Qwen3 等通用模型（MLX / Ollama）、Embedding | Xiaomi-OCR-0 在 macOS 上只有社区 GGUF/Ollama 版本，官方标注为实验性且未完整验证，需实测后再用于生产 |

同一套 Docker Compose 支持"全云 / 云+本地推理 / 全本地"三种形态，差别只在 LiteLLM 的路由配置。

### 5.3 Rust 与 Python 分工

| 模块 | 语言 | 理由 |
|---|---|---|
| `fos-edge` 边缘采集（Modbus RTU/TCP、OPC UA、串口仪表、断网缓存、上行） | **Rust** | 长期无人值守运行在工控机/树莓派级设备上，要求稳定、低资源；`tokio-modbus`、`async-opcua` 可直接用 |
| `fos-protocol` 数据模型（点位、事件的 Protobuf/JSON Schema） | Rust（同时生成 Python 类型） | 边缘与云共享契约 |
| Agent 内核、MCP 工具、OCR 管线、行业包、API | **Python** | 生态最全，迭代最快；2 人团队开发速度优先 |
| 后期热点（策略判定、审计写入、网关） | 视压测结果迁移到 Rust | 3 个月内不提前优化 |

### 5.4 直接复用的开源组件

| 用途 | 组件 | 许可证 |
|---|---|---|
| OCR | Xiaomi-OCR-0 | Apache-2.0 |
| 版面检测（可选，规整文档并行加速） | PP-DocLayoutV3（PaddleX） | Apache-2.0 |
| 推理服务 | vLLM / SGLang | Apache-2.0 |
| LLM 网关 | LiteLLM | MIT（企业功能另有许可，只用开源部分） |
| Agent 框架 | **AgentScope**（阿里开源，和手册同一生态） | Apache-2.0 |
| MCP | MCP 官方 Python / Rust SDK | MIT |
| 向量检索 | pgvector | PostgreSQL 许可 |
| Agent 观测与评测 | Langfuse | MIT（核心） |
| 后端 | FastAPI + SQLAlchemy + Alembic | MIT |
| 前端控制台 | Next.js + shadcn/ui | MIT |
| 边缘 | tokio-modbus、async-opcua、rumqttc | MIT/Apache-2.0/MPL-2.0 |

## 6. 仓库结构

```
factory-ai-native-os/
├── crates/                      # Rust
│   ├── fos-edge/                # 边缘采集
│   └── fos-protocol/            # 共享数据契约
├── fos/                         # Python 核心 OS
│   ├── kernel/                  # Run/Session/Workspace/Policy/Evidence、调度
│   ├── gateway/                 # LiteLLM 配置、MCP 网关、Agent 网关
│   ├── perception/              # OCR 管线（Xiaomi-OCR-0）、语音
│   ├── tools/                   # 通用 MCP 工具（查询、写入、通知）
│   ├── channels/                # 钉钉/企业微信/飞书接入
│   └── api/                     # FastAPI
├── packs/
│   └── refractory/              # 耐火材料行业包：本体、单据 Schema、Skills、日报模板、评测集
├── tenants/
│   └── luneng/                  # 六安绿能租户配置（不含密钥）
├── web/                         # 控制台
├── deploy/                      # docker-compose（cloud / hybrid / local 三套 profile）
├── evals/                       # 黄金数据集与回归
└── docs/
```

工程规范：Python 用 `uv` + `ruff` + `pytest`；Rust 用 cargo workspace + `clippy` + `cargo-deny`；GitHub Actions 跑测试与评测回归；每个合并到 main 的版本即一个可回滚的 Agent Release。

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| 只有 2 人，范围过大 | 严格按 P0 → P1 → P2；每周演示后砍需求；能托管就不自建 |
| 工人不愿意用 | 入口放在已有 IM 里；拍照即可，不填表；先找 2–3 个积极的班组长试点 |
| 窑炉仪表没有通讯接口 | 加装低成本无线测温 / 拍照抄表 OCR 兜底 |
| 手写单据识别不准 | Xiaomi-OCR-0 支持手写；L2 确认卡片兜底；逐步把高频单据改成标准模板 |
| 大模型乱编数据 | 数字只来自数据库工具结果，模型不允许"估算"；回答附来源记录 |
| 云 API 成本 | LiteLLM 按租户计量 + 预算上限；简单任务路由到便宜模型 |
| 数据合规 / 客户不愿上云 | 同一套代码支持本地 DGX 部署 |
| 行业包抽象过早或过晚 | 第一家工厂的代码先写在 `packs/refractory`，W13 用第二套租户验证抽象是否成立 |
